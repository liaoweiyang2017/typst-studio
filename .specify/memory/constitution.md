# Typst Studio 项目原则

版本：1.0.0。记录日期：2026-10-17。流程依据：用户当日明确要求。

## 规范先行

采用 GitHub Spec Kit 的规范驱动开发流程：项目原则 → specify/clarify → plan → tasks → 一致性检查 → implement → 验收。
每轮先写清目标用户、需求、范围、非目标、边界条件、业务规则和可验证的验收标准，再制定方案与任务。需求编号贯穿方案、任务、测试和交付记录。

## 实施确认

用户确认本轮范围、技术方案和任务清单后，才能进入大规模编码。历史版本的发布授权不能代替新一轮方案确认。
确认前可读取代码、研究实现、整理规范和提出验证方案。未界定的功能保持待确认，不拆成多次“小改动”绕过确认。记录确认消息、时间和对应文档版本；未收到回复不代表确认。

## 实现与偏差

按已确认任务逐项实现，并对照验收标准记录通过、失败、未验证及证据。测试覆盖真实行为、关键边界、数据安全和性能风险，避免只检查方法存在或复制实现逻辑。
发现需求冲突或实现偏差时，先说明冲突、证据、影响与修正方案。会改变已确认范围、用户行为、架构或验收标准的修正，先取得用户确认；独立且仍符合已确认规范的工作可继续。

## 项目约束

- Mac 保持 Swift 原生；Windows 保持 WinUI 3 与 Fluent Design。当前 Windows 后端使用 Tinymist、PDFium，编辑器使用 WinUIEdit/Scintilla；架构变更须说明理由和迁移代价。
- 优先复用经过核实的实现，保持模块简单、便于人工维护。避免为未确认的未来需求引入框架或抽象层。
- 用户源码、未保存修改、换行形式和外部修改冲突必须受到保护。源码映射应验证中文、公式和跨文件情形。
- 编译、搜索和渲染的长耗时工作不得阻塞界面。性能阈值须指定测试环境、项目规模与测量口径，不能把防抖时间当成完成时间。
- 源码在私人仓库，安装包在公开 Release；采用本地构建，不新增 GitHub Actions。Windows 发布保持独立标签与 Mac 更新源隔离。
- 发布前记录架构、版本、测试证据、文件校验和及限制；模拟运行不等于实体设备验证，未执行的检查不得写成通过。
