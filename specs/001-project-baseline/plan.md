## 现有技术边界

保留 Swift Mac 端与 WinUI 3 Windows 端。Windows 的 UI、可移植业务逻辑、编译会话、PDF 渲染各沿现有模块维护。先评估现有组件能否满足已确认需求，再决定是否增加依赖。

## 后续规划方法

1. 将新需求映射到 FR/AC 编号，明确本轮范围、非目标和待决问题。
2. 针对受影响模块列出数据流、异步取消/版本处理、错误状态、配置兼容与回退方案；逐项说明为什么需要改动。
3. 建立验收矩阵：AC 编号 → 代码位置 → 必要测试 → 运行环境 → 证据 → 结果。性能项先建立基准，再提出可验证目标。
4. 将可独立交付的场景拆为任务，记录依赖和完成条件，避免无关重构。
5. 对照规范检查遗漏与冲突，向用户提交具体方案及任务清单，取得确认后实施。

## 验证分层

- Core 测试：缓冲区、搜索、符号上下文、位置转换和边界条件。
- 原生集成：实际 Tinymist 和 PDFium，不以模拟返回值代替编译/定位证据。
- WinUI 验证：显示、交互、取消和布局，数据数量断言不能替代真实可见控件与截图。
- 发布验证：架构、运行依赖、安装、版本和校验和；每项保留环境与限制说明。

具体模块变更、测试阈值、工时和版本仍待本轮需求明确后制定。本草案不包含已获准执行的产品改动。
